# 从上下文创建 GitHub Issue

把已讨论内容或指定文档整理成一个可执行、可审阅的 GitHub 议题（Issue）。运行期间保持工作区只读；唯一允许的持久化写操作，是用户确认后的 Issue 创建。

## 边界

- 只使用当前对话和用户明确点名、附加或提供路径的文档。不要为了补充内容而扫描仓库或读取无关文件。
- 不得创建、编辑、删除或格式化代码、文档、配置及其他工作区文件；不得执行提交、推送、切换分支或其他 Git 写操作。
- 可以运行解析目标仓库、检查 GitHub 认证等只读命令。
- 不得在 Issue 中发布密钥、令牌、个人信息或其他敏感内容。发现疑似敏感信息时停止整理，请用户提供脱敏内容；不要在回复中重复该信息。
- 只支持 GitHub，不要自动改用 GitLab 或其他平台。

## 整理来源

1. 明确本次使用的对话片段和文档。用户说“前面讨论的内容”时，只采用与当前任务相关的已完成讨论。
2. 从来源中提取事实、目标、明确需求、验收标准、参考资料和未决问题。允许把明确需求改写成可验证的表述，但不得补造来源没有支持的范围、方案或约束。
3. 默认每次只创建一个 Issue。若来源包含多个彼此独立的任务，先给出拆分建议并让用户选择；在选择前不要进入发布步骤。
4. 使用来源的主要语言；无法判断时跟随用户当前使用的语言，中文语境默认使用中文。

## 确定目标仓库

按以下优先级解析 GitHub 仓库：

1. 用户明确提供的 `owner/repo`。
2. 当前 Git 仓库的 `origin` 远程地址；只接受可明确解析为 `github.com` 仓库的 HTTPS 或 SSH 地址。
3. 若仍无法确定，询问用户提供 `owner/repo`。

不得根据目录名、组织名或文档内容猜测仓库。目标仓库未确定前，只能生成草稿，不能发布。

## 生成 Issue 草稿

- 标题应简洁描述要解决的问题或期望结果，避免使用“处理一下”“优化”等无法独立理解的措辞。
- 正文按来源内容选用以下章节，空章节不要输出：
  - `## 背景`
  - `## 目标`
  - `## 需求`
  - `## 验收标准`
  - `## 参考资料`
  - `## 待确认事项`
- 仓库内文档使用相对仓库根目录的路径。不得发布本机绝对路径；仓库外的本地文件只保留安全、必要的文件名或文字说明，不生成不可访问的本地链接。
- 标签、负责人和里程碑默认留空，仅在用户明确指定时加入。
- 将未被来源确认的内容放入“待确认事项”，不要把假设伪装成事实或验收标准。

## 预览与确认

发布前必须展示完整预览，至少包含：

- 目标仓库 `owner/repo`
- Issue 标题
- Issue 正文
- 用户明确指定的标签、负责人或里程碑（如有）

预览后明确询问用户是否按展示内容发布。只有用户在看到本次完整预览后作出明确肯定答复，才视为发布授权。最初的“创建 Issue”请求、模糊回复或对旧版本草稿的确认都不能替代这一步。

## 发布

1. 使用 GitHub 命令行工具（GitHub CLI，`gh`）执行 `gh auth status`。认证无效时停止，保留草稿并提示用户运行 `gh auth login -h github.com`；不要自动登录或自动重试。
2. 使用 `gh issue create --repo OWNER/REPO` 发布已经确认的标题和正文，并仅附加用户明确指定的元数据。
3. 命令成功后返回新 Issue 的链接，并简要说明已发布到哪个仓库。
4. 命令失败时报告原始原因的简明摘要并继续保留草稿。不要自动重试，也不要通过修改工作区文件绕过失败。

发布前后都不得修改工作区。如果命令需要正文文件，只能使用仓库外的临时文件，并在命令结束后清理。
